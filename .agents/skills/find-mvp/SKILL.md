# Find Mvp

Find the smallest build that can deliver the core value, test the central assumption, or unblock the next consequential decision. Preserve all excluded ideas as future problems instead of losing them.

## Interview

1. Inspect the available codebase, documents, and project context before asking questions. Answer questions through investigation whenever possible.
2. Interview the user relentlessly, asking exactly one question at a time. With each question, provide a recommended answer and concise rationale.
3. Establish the target user, painful problem, promised outcome, riskiest assumption, essential journey, success signal, constraints, and acceptable manual work.
4. Challenge every proposed capability. Keep it in the MVP only when omitting it prevents delivery of the core value, prevents testing the central assumption, or creates an unacceptable safety, legal, or operational failure.
5. Treat polish, scale, automation, flexibility, secondary personas, uncommon edge cases, speculative integrations, and premature architecture as future problems unless the evidence makes them essential now.
6. Resolve dependencies in order. Revisit earlier answers when a later decision invalidates them.
7. Continue until every material item has a clear classification and the user and Codex share the same MVP boundary.

## Output

Conclude with:

- the user, problem, and core value proposition;
- the smallest end-to-end MVP journey;
- the capabilities that must be built now and why;
- explicit non-goals;
- a future-problems list containing every deferred idea, with the trigger or evidence that would justify revisiting it;
- the main assumption being tested and the success/failure signal;
- the next concrete build step.

Do not allow “we might need it” to qualify an item for the MVP. Do not discard scope silently: anything excluded must be captured as a future problem.
