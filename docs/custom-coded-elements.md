# Custom coded elements

Catalog authoring has Group, Element, and Code List views. Custom groups and elements use the `opentriage.org` namespace automatically; NEMSIS elements retain their standard NEMSIS identifiers. The Element ID and Group ID are permanent identities and are shown with those names in the editor. Stored custom element keys include an organization-specific prefix so two organizations can choose the same Element ID without colliding. The Element view lists and searches both standard NEMSIS and custom elements, and creates every custom datatype through one form. Standard NEMSIS definitions are read-only except for labels. The Group view inspects standard groups and creates or renames custom groups. The Code List view edits code-list content, including custom coded choices.

An administrator creates a custom coded element in a catalog draft with a stable UUID, a fixed `opentriage.org` namespace and an administrator-chosen Element ID, a custom code system URI, and one or more stable code/label pairs. Element IDs may contain periods between nonempty parts, such as `eDisposition.02_se`; the custom namespace keeps that identifier distinct from NEMSIS `eDisposition.02`. The optional `nemsisElement` and per-choice `nemsisCode` fields record mappings to the pinned NEMSIS 3.5.1 catalog. They do not replace the custom element or code identity. Mapped codes must exist for the mapped element in that catalog release. Published definitions are immutable and travel with the pinned release.

The potential NOT codes are `7701001`, `7701003`, and `7701005`. The potential pertinent negative codes are the NEMSIS 3.5.1 `eCustomConfiguration.08` enumeration. A definition may permit a subset. A form field separately enables exceptional codes and chooses the order and enabled subset of ordinary and NOT choices. The form editor displays readable NOT labels and owns code enablement and ordering; the catalog editor has no enablement or reordering controls. Codes disabled by legacy catalog settings remain available for explicit selection in new form policies, while existing published forms retain their pinned behavior. The runtime control uses that effective policy in both clinical views. Reports store the chosen code and its custom code system, with NOT and pertinent negative attributes stored separately, so save and reload preserve them.

To add a local option to an eligible existing NEMSIS list, edit that list in the catalog authoring view. A custom coded element has its own identity and cannot claim the NEMSIS code system. It does not expand a restricted standard list.

Custom definitions can allow one or multiple values per target. A target can be the report root, a repeated medication entry, or a repeated assessment entry. The clinician sees each target entry in both views; the stored result binds to that entry's stable group instance ID. Moving the field to another visual section does not change the binding. The target and recurrence are part of the published immutable definition, so a new identity is required to change either.
