# Custom element groups in NEMSIS 3.5.1

The pinned `apps/web/app/data/nemsis-3.5.1-sources/xsd/eCustom_v3.xsd` defines repeated `eCustomConfiguration.CustomGroup` entries. Each has a required `CustomElementID`, and `eCustomConfiguration.09` supplies an optional `CorrelationID` shared by related custom definitions. The result side defines repeated `eCustomResults.ResultsGroup` entries: `eCustomResults.01` is repeatable, `.02` identifies the custom element, and `.03` optionally correlates a result with a patient-report entry. It does not define recursive custom groups.

An authored group is therefore a flat, organization-owned correlation identity. Its member fields carry the same immutable `groupDefinitionId` in the pinned catalog and form. The group's title is presentation metadata; its ID, namespace, slug, recurrence, and supported standard parent are stable. A result belongs to a custom group instance, which has its own stable ID and an explicit standard parent instance ID. This preserves two responses against different medication or assessment entries, and multiple group instances under one entry when recurrence permits. A form section and its name only control placement. Moving a member field never changes membership or stored value relationships.

Only report root, `eMedications.MedicationGroup`, and `eExam.AssessmentGroup` can be parents. Custom groups cannot contain custom groups. The database verifies the authored group and member field against the report-pinned catalog/form, parent identity, and single-group cardinality; the clinical editor uses the same stable IDs. XML interchange remains outside this slice.
